CDN 部署说明

本说明面向 GLOWMAG 指甲电商独立站，阐述 Cloudflare CDN 的完整部署流程：域名接入、源站打通（Tunnel / 反代二选一）、TLS、缓存策略、WAF 安全防护、兜底容灾与日常运维验证。对齐仓库 docs/deploy.md §2.1、高可用架构设计-v2.md §7.0 与 上线检查清单.md §1。

项目：GLOWMAG（nailshop） 入口：Cloudflare DNS / CDN / WAF 版本：v1.0 更新：2026-08-28

1概述与收益

GLOWMAG 采用「源站最小暴露 + Cloudflare 前置」的入口架构：域名 NS 托管至 Cloudflare，公网流量全部经 CF 的 CDN 边缘节点进入，源站（单机 Docker Compose）只承接回源请求。

1.1 CDN 在本项目中承担的四类角色

角色说明对应架构纪律
内容分发（CDN）静态资源（JS/CSS/图片/字体）缓存在全球边缘节点，用户就近命中，源站只承受动态请求架构 v2 §7.0「静态资源+缓存挡掉大半流量」
安全防护（WAF）TLS 终止、CC 攻击防护、Bot 拦截、Rate Limiting，脏流量在边缘被丢弃架构 v2 §7.0「入口交给 Cloudflare」
高可用入口DNS 多活；源站故障时边缘仍可服务缓存页与兜底静态页架构 v2 §2.1 接入层「用户永远打得开」
零暴露通道cloudflared Tunnel 方案下源站可不开放任何公网端口，仅出站连接deploy.md §1「8000 与 3306 绝不对公网开放」

1.2 收益量化（单机阶段）

  • 源站压力：静态资源全走 CDN 后，回源请求只剩 API 动态调用，单台 4C8G 可承载日 PV 10-30 万（架构 v2 §7.0 容量天花板经验值）；
  • 延迟：静态资源命中边缘节点（TTFB 通常 <50ms），首屏 LCP 目标 <2.5s（4G）依赖 Hero 图 AVIF + CDN 分发；
  • 成本：Cloudflare 免费计划已覆盖 CDN/WAF/无限 DDoS 防护，Pro（$20/月）解锁更多 WAF 规则与图片优化；单机全套（服务器+CDN+备份）预算 $100/月内；
  • 可用性：入口高可用交给云，源站整机宕机时 CF 仍能服务缓存内容与兜底品牌页。

为什么选 Cloudflare 而非传统 CDN：① 免费计划即含 WAF 与无限 DDoS；② 与 Tunnel/R2/Origin CA 一体化，无需另购证书与专线；③ 国内服务器虽无 CF 中国节点，本项目目标市场为海外 DTC（美/欧），边缘节点覆盖正好匹配。

2架构中的位置

流量自上而下：用户 → Cloudflare 边缘（DNS/WAF/CDN/TLS）→ 源站入口（Tunnel 或 Caddy）→ Docker Compose 内的 api 容器（仅绑 127.0.0.1:8000 或容器内网）。

┌──────────────────────────────┐ [用户/海外买家] ──► │ Cloudflare 边缘节点 │ │ DNS · WAF · Rate Limit · TLS │ │ CDN 缓存(静态资源/图片) │ └──────────┬───────────────────┘ │ 回源(仅动态请求) ┌────────────────┴─────────────────┐ │ 方案A: cloudflared Tunnel(出站) │ ← 推荐,零开放端口 │ 方案B: Caddy 反代(80/443) │ └────────────────┬─────────────────┘ │ 127.0.0.1:8000 / 容器内网 ┌──────────┴───────────┐ │ Docker Compose │ │ api(8010) worker │ │ mysql(3306 不出网) │ └──────────────────────┘ 缓存命中: 静态资源在边缘直接返回(不回源) 回源命中: /api/* 动态请求 → 源站计算 兜底: 源站不可达 → CF 服务缓存页/静态兜底页

4第一步：域名接入 Cloudflare

  1. 添加站点
    CF 控制台 → Add a domain → 输入裸域（如 glowmag.com） → 选择 Free 计划。CF 会自动扫描现有 DNS 记录并导入。
  2. 修改注册商 NS
    CF 会分配两个 NS（形如 xxx.ns.cloudflare.com）。到域名注册商的 DNS 管理页，将 NS 修改为这两个地址。生效通常 5 分钟～24 小时（TTL 决定），CF 站点页显示 Active 即完成。
  3. 配置 DNS 记录
    在 CF DNS 面板按下表添加（Proxy 状态决定是否走 CDN）：
    类型名称内容Proxy用途
    A / AAAA@（裸域）源站公网 IP橙云 ON主站（方案 B 必须；方案 A 可仅留 Tunnel 的 CNAME）
    A / AAAAwww同上橙云 ONwww 跳转
    CNAME<tunnel-id>.cfargotunnel.com—橙云 ON方案 A：由 Tunnel 的 Public Hostname 自动创建，无需手动
    CNAMEcdnR2 自定义域（§9）橙云 ON可选：图片走 R2 + CDN

    橙云 vs 灰云：橙云（Proxied）= 流量经 CF CDN/WAF，真实源站 IP 被隐藏；灰云（DNS only）= 纯 DNS 解析直连源站。本站点所有对外记录一律橙云。灰云仅在排障临时切换时使用，且切换会暴露源站 IP，用完务必改回。

  4. 开启全站 HTTPS 跳转
    CF → SSL/TLS → Edge Certificates → 打开 Always Use HTTPS。至此 HTTP 流量在边缘被 301 到 HTTPS。

5第二步：源站接入（二选一）

对应 deploy.md §2.1。两方案只能选一个作为主入口，方案 A（Tunnel）为默认推荐。

5.1 方案 A：cloudflared Tunnel（推荐，零开放端口）

原理：源站运行 cloudflared 守护进程，主动向 CF 建立出站加密隧道；公网流量经边缘节点逆行进隧道到达内网服务。源站不需要任何入站端口，防火墙可只留 22。

  1. 创建 Tunnel
    CF 控制台 → Zero Trust → Networks → Tunnels → Create a tunnel → 选择 Cloudflared 类型 → 命名（如 glowmag-prod）→ 记下页面上显示的 Token（一长串 base64）。
  2. compose 追加 tunnel 服务
    在仓库根 docker-compose.yml 末尾追加（与 api 同网络 glowmag-net，直连容器名，不经过宿主端口）： 
      tunnel:
    image: cloudflare/cloudflared:latest
    container_name: glowmag-tunnel
    restart: unless-stopped
    command: tunnel --no-autoupdate run --token ${CF_TUNNEL_TOKEN:-}
    networks: [glowmag-net]
  3. .env 注入 Token
    .env 追加一行（Token 属密钥，永不入库，与 GM_JWT_SECRET 同等纪律）： 
    CF_TUNNEL_TOKEN=eyJhIjoixxxxxxxxxxxxxxxxxxxx...
  4. 配置 Public Hostname
    回到 Tunnel 详情页 → Public Hostname → Add a public hostname：
    字段值说明
    Subdomain / Domainglowmag.com（或 www）绑定对外域名，CF 自动建 CNAME 记录
    TypeHTTPTunnel 到源站走容器内网明文即可（外段仍是 HTTPS）
    URLapi:8000容器名直连，非 127.0.0.1（tunnel 容器内 127.0.0.1 是它自己）
  5. 启动并验证 
    cd /opt/nailshop && docker compose up -d          # tunnel 随编排拉起
docker compose logs -f tunnel                    # 看到 "Registered tunnel connection" ×4 即成功
curl -sI https://glowmag.com/api/health          # 期望 200 + 响应头含 cf-ray

优点：零开放端口（安全组只剩 22）、源站 IP 天然不暴露、无需续证（证书在 CF 边缘与隧道内自动协商）、换服务器只改 Tunnel 指向不停 DNS。代价：多一个常驻容器（内存约 30MB）；隧道断线即入口全断（cloudflared 自动重连，编排 restart: unless-stopped 兜底）。

5.2 方案 B：源站反代（Caddy）+ 橙云 Full (strict)

原理：宿主机装 Caddy 做 HTTPS 反代并监听 80/443，CF 橙云回源到 Caddy。适用：Tunnel 不适用（如需 WebSocket 长连接调优、源站在 CF 网络质量差的区域）或希望保留直连 IP 冗余通道的场景。

  1. 安装 Caddy（Debian/Ubuntu 官方源），Caddyfile 一行反代： 
    glowmag.com {
    reverse_proxy 127.0.0.1:8000
}
    Caddy 会自动申请/续期公共证书；配合 CF 建议改用 Origin CA 证书（15 年有效，仅 CF 信任）：CF → SSL/TLS → Origin Server → Create Certificate → 证书/私钥存入 /etc/ssl/caddy/，Caddyfile 对应改为 tls /path/cert.pem /path/key.pem。
  2. CF 侧 SSL 模式
    CF → SSL/TLS → Overview → 设为 Full (strict)（回源验证证书，防中间人）。禁止用 Flexible（回源走 HTTP 且易造成重定向循环）。
  3. 防火墙放行：安全组开放 80/443（仅此方案需要）。可选加固：80/443 的入站规则只放行 CF 回源 IP 段，其余直连扫描全部拒绝。
  4. 验证：curl -sI https://glowmag.com/ 期望 200，且 server: Caddy 头已被 CF 隐藏。

5.3 两方案对比

方案 A · Tunnel（推荐）方案 B · Caddy 反代

6第三步：TLS / HTTPS 配置

所有配置位于 CF → SSL/TLS → Edge Certificates：

配置项推荐值说明
SSL/TLS 模式Full (strict)端到端加密 + 回源验证书。Flexible 会引发重定向循环且不安全
Minimum TLS VersionTLS 1.2支付场景（Stripe）要求至少 1.2；不建议 1.0/1.1
Always Use HTTPSONHTTP 301 → HTTPS
HSTS (Strict Transport Security)启用， max-age=6 个月强制浏览器后续只走 HTTPS。注意：启用前确认全站资源无 http:// 混载，否则无法回退（浏览器侧不可撤销）
Minimum TLS + 证书覆盖裸域 + www + cdn 全覆盖Edge Certificate 免费且自动续期，确认覆盖所有子域
TLS 1.3ON握手更快，现代浏览器全支持

支付链路提示：Stripe Checkout/ webhook（https://glowmag.com/api/payments/webhook）依赖合法证书链。Full (strict) + 自动续期已满足；切勿在生产使用自签证书或 Flexible 模式，Stripe 侧会校验失败。

7第四步：缓存策略配置（Cache Rules）

CDN 的核心收益在本步兑现。配置位于 CF → Caching → Cache Rules（新版规则引擎，替代旧 Page Rules）。

7.1 默认行为（不动配置时的基线）

  • CF 默认只缓存静态扩展名（js/css/png/jpg/webp/avif/woff2/svg/gif/ico/pdf 等），HTML 与 /api/* 默认不缓存（cf-cache-status: DYNAMIC）；
  • 带 Set-Cookie / Authorization 头的响应不缓存；
  • 默认遵循源站 Cache-Control 头——api 容器对静态资源已输出长缓存头（Vite 构建产物带 hash 文件名，可安全 immutable）。

7.2 推荐规则集（按优先级从上到下）

#规则名匹配条件（示例）动作目的
1api-bypassURI Path starts with /api/Bypass cache下单/鉴权/购物车等动态接口绝不缓存（宁可慢不可脏数据）
2admin-bypassURI Path starts with /adminBypass cache后台页面含登录态，不缓存
3assets-longURI Path starts with /assets/Eligible for cache，Edge TTL = 1 month，Browser TTL = 1 yearVite hash 产物，内容变即换名，可超长缓存
4images-cache文件扩展名 in（webp, avif, jpg, png, svg, woff2）Eligible for cache，Edge TTL = 7 days图片与字体集中缓存，命中即不回源
5html-short（可选）Hostname eq glowmag.com 且内容类型 text/htmlEdge TTL = 5 min + stale-while-revalidateSPA 入口 HTML 短缓存：源站挂了 5 分钟内边缘照常出页（兜底缓冲）

7.3 缓存键与查询参数

  • 查询字符串：默认全部纳入缓存键。图片若用 CDN 参数变体（如 ?w=400&q=75，见详细设计文档图片管线），保持默认即可——不同参数各自缓存，不会串；
  • 上架上新：商品图 URL 不变但内容更新时，用 Cache Purge（§7.4）按 URL 精准清除，不要全局 Purge Everything（会瞬间打空缓存，回源洪峰）；
  • 登录态页面：凡响应可能含用户个性化内容（购物车抽屉数据、账户页）的一律走 /api/ 动态接口 + Bypass 规则，不要把登录态 HTML 推上边缘缓存。

7.4 清除缓存（Purge Cache）的正确姿势

  1. 发布新版本后：hash 文件名变化，无需清缓存（新 URL 自动 Miss 回源，旧的自然过期）；
  2. 替换了同名图片/首页 Hero：CF → Caching → Configuration → Purge by URL（精准）或 Purge by hostname/tag（Pro）；
  3. 仅排障时才 Purge Everything，操作后密切观察回源 QPS 与源站负载。

7.5 验证缓存生效

# 第一次请求（边缘未命中，回源）
$ curl -sI https://glowmag.com/assets/index-B1x2.js | grep -i 'cf-cache-status\|age\|cache-control'
cf-cache-status: MISS
age: 0

# 第二次请求（边缘命中，不再回源）
$ curl -sI https://glowmag.com/assets/index-B1x2.js | grep -i 'cf-cache-status\|age'
cf-cache-status: HIT
age: 37

# 动态接口必须不缓存
$ curl -sI https://glowmag.com/api/catalog/products | grep -i cf-cache-status
cf-cache-status: DYNAMIC

关注 cf-cache-status 取值：HIT 边缘命中 ／ MISS 未命中回源 ／ EXPIRED 过期回源 ／ DYNAMIC 默认不缓存（动态） ／ BYPASS 规则显式绕过 ／ REVALIDATED 协商缓存生效。

8第五步：安全防护（WAF / 限流 / 端口纪律）

8.1 WAF 托管规则

  • CF → Security → WAF → Managed rules → 启用 Cloudflare Managed Ruleset（免费计划可用基础集，Pro 解锁更多）；
  • 安全等级（Security Level）默认 Medium 即可；对已知恶意流量高峰可临时调 High；
  • Bot Fight Mode 开启（免费）——拦截明显爬虫/扫描器。注意 Stripe webhook 是合法机器流量，若被误拦在 WAF 事件里为其 UA/IP 加白。

8.2 Rate Limiting（对齐源站 Nginx 纪律）

架构 v2 §2.2 要求「IP 60r/min，checkout 独立更高阈值」，在 CF 侧同样分层配置（CF → Security → WAF → Rate limiting rules，免费计划含 1 条规则）：

规则匹配阈值动作
全站防扫任意路径同 IP > 300 req / 1 minBlock 10 min（挑战页）
登录防爆破/api/auth/*、/admin同 IP > 20 req / 1 minManaged Challenge
结账保护/api/checkout、/api/payments/*阈值放宽（真人下单高峰不受误伤），异常特征交给 WAF观察 → Block

8.3 端口与回源纪律（源站侧）

  • 安全组仅放行：22（SSH，建议限管理 IP）；方案 A 到此为止，方案 B 另加 80/443（可限 CF 回源段）；
  • 8000（api）与 3306（MySQL）绝不对公网开放——api 只绑 127.0.0.1:8000，MySQL 端口不映射宿主，仅 glowmag-net 内网；
  • 禁止在 DNS 面板为调试开灰云直连（暴露源站 IP）；源站 IP 若曾泄露，换 IP 或用 Tunnel 后在 CF 侧开 IP Access Rules 拦截直连 Host 头非本站的请求。

分层防线总结：脏流量（DDoS/Bot/扫描）在 CF 边缘丢弃 → 漏网突刺被 Rate Limiting 挑战 → 源站 Nginx/应用层限流兜底 → 数据库只在内网。任何一层失效，下层仍能独立工作。

9静态资源与图片优化（CDN 前后配合）

9.1 构建产物（已在交付中落地）

  • 前后台 Vue SPA 构建产物在 web/dist（前台在根、后台 admin/），随 api 镜像分发；Vite 产物文件名带内容 hash → 配合 §7 规则 3 的 1 年浏览器缓存 + 1 月边缘缓存，改版零 purge；
  • 首屏 LCP 关键：Hero 图 priority 预载 + AVIF/WebP 格式（目标 <2.5s @4G），AVIF 走 CDN 边缘分发后 TTFB 通常 <50ms。

9.2 图片管线两种模式

模式做法适用
模式 1：源站出图 + CDN 缓存（当前默认）图片随 web/dist 或 api 静态目录分发，经主域名橙云缓存（§7 规则 4）MVP 商品图量小，零额外运维
模式 2：R2 对象存储 + 自定义域CF R2 建 bucket（如 glowmag-media）→ 绑自定义域 cdn.glowmag.com（自动走 CDN，R2 出口流量免费）→ 后台上传图片写 R2，商品表 images 存 https://cdn.glowmag.com/…图片量大后迁移；环境变量 R2_ACCOUNT_ID / R2_ACCESS_KEY / R2_SECRET / R2_BUCKET（详细设计 §10）

R2 的双重身份：除图片托管，R2 同时承载每日数据库备份异地上传（deploy.md §4.1：rclone copy … r2:glowmag-backups/）。备份 bucket 与媒体 bucket 分开，权限仅写不允许公开列举。

9.3 rclone 配置 R2（备份/媒体上传共用）

# ~/.config/rclone/rclone.conf

10兜底页与故障转移（接入层高可用）

对应架构 v2 §2.1：源站故障时「用户永远打得开」。三道防线按时间窗递进：

防线触发机制用户看到
① 边缘缓存继续服务源站宕机 <HTML 缓存 TTL（§7 规则 5 的 5 min 窗口）Edge TTL 内的 HTML/静态资源照常命中页面正常（数据接口报错，前端有降级 UI）
② 兜底静态页源站宕机 > 缓存窗口，回源 5xx/超时CF Rules → Settings → Origin Error Pages 自定义，或用 Workers/ Serve Rules 在 origin_error 时返回托管在 CF Pages 的品牌静态页（含 logo、客服邮箱、社媒链接）品牌页：「我们马上回来 + 联系方式」
③ 缓存+托管内容长时间宕机静态资源（js/css/图）仍在边缘服务；配合 Cloudflare 的 Always Online（如启用）至少资源可访问，配合 ② 的品牌页保住信任

10.1 兜底页制作要点

  • 内容三要素：品牌视觉（logo/品牌墙）＋ 客服邮箱（support@glowmag.com）＋ 社媒入口；不依赖任何源站资源（全部内联或托管在 CF）；
  • HTTP 503 + Retry-After 头，避免搜索引擎降权；
  • 已下单用户：宕机恢复后由 worker 的订单确认邮件补发（outbox 落库必达纪律，架构 v2 §2.4），不依赖兜底页承接交易。

11监控与验证

11.1 CF 自带观测（免费够用）

  • Analytics：流量/带宽/缓存命中率（Cache Hit Ratio，目标 >85%）/ 请求分布国家；命中率低先查 §7 规则覆盖；
  • Security Events：WAF/Rate Limit 拦截明细，定期review是否有合法流量（如 Stripe webhook、UptimeRobot 拨测）被误拦；
  • Tunnel 健康：Zero Trust → Tunnel 页看连接数（正常 4 条 HA 连接）。

11.2 外部拨测（上线检查清单要求）

  • UptimeRobot（或同类）每 1 min 拨测四链路：首页 / 加购 / 搜索 / checkout，地域覆盖美/欧（目标市场）；
  • 拨测告警对接：邮件 + 即时通讯，P0（支付/不可用）电话级。

11.3 日常巡检命令（服务器侧）

# 入口链路（经 CF）
curl -sI https://glowmag.com/api/health          # 200 + cf-ray
curl -sI https://glowmag.com/ | head -1          # 200

# 源站本地（排除 CF 因素）
curl -s http://127.0.0.1:8000/api/health         # {"ok":true,...}

# Tunnel 状态
docker compose ps tunnel
docker compose logs --tail=20 tunnel

# 缓存命中率抽样（连续 10 次静态资源）
for i in $(seq 1 10); do curl -sI https://glowmag.com/assets/index-B1x2.js \
  | grep -i cf-cache-status; done | sort | uniq -c

12大促 / 流量高峰的 CDN 侧动作

对齐架构 v2 §3 大促预案与 deploy.md §5 扩容表，CDN 侧在预热阶段完成以下动作（应用侧扩容见对应文档）：

阶段CDN 动作说明
预热（上线前）CDN 预热 Hero 图与活动页素材发布前对关键资源 URL 主动请求一遍（脚本 curl 列表），使边缘提前 MISS→HIT；避免 0 点集中首访回源洪峰
预热缓存规则临时全量化deploy.md §5「CF 侧开缓存规则（静态站全量缓存）」：对活动落地页 HTML 延长 Edge TTL（如 10 min）+ stale-while-revalidate
洪峰中Rate Limiting 生效即防线非核心接口（评价提交/UGC）先限（应用层配合）；列表页全走缓存
洪峰中观察回源 QPSAnalytics 实时视图，回源占比突增 = 缓存键设计问题，立即检查是否有新参数变体爆炸
会后规则回调 + 精准 purge活动页 URL 按 URL purge；把临时 TTL 规则恢复常规值

13常见问题排查

症状排查步骤常见根因 → 处置
CF 502 / 504① curl http://127.0.0.1:8000/api/health（服务器上）② 本地通 → 查 Tunnel/Caddy：docker compose logs tunnel ③ 本地不通 → 看 api 日志（多为 .env 缺失或迁移未跑）Tunnel 断连 → 容器自动重连，仍断查 Token；Caddy 反代地址写错（127.0.0.1 vs 容器名 api 混用）→ 对照 §5 改 URL；api 重启循环 → 按 deploy.md §6 处置
重定向循环（ERR_TOO_MANY_REDIRECTS）CF SSL 模式是否 Flexible源站强制 HTTPS + CF Flexible 回源 HTTP → 死循环。改 Full (strict)（§6）
接口返回旧数据 / 购物车串号curl -sI …/api/xxx 看 cf-cache-status 是否 HIT动态接口被缓存 = Bypass 规则没生效（规则顺序/匹配写错）→ 把 api-bypass 置顶；或源站误给 API 下发了缓存头
新版本发布后样式/JS 还是旧的检查资源 URL 是否换了 hash 文件名正常情况无需 purge；若 HTML 被缓存（§7 规则 5）持有旧引用 → 按 URL purge 首页 HTML；不要习惯性 Purge Everything
Stripe webhook 收不到 / 403CF Security Events 搜 payments/webhook 是否被 WAF/Rate Limit 拦合法机器流量被 Bot 规则误拦 → 对 /api/payments/webhook 加 WAF 例外（Skip 规则），Stripe 侧确认回调地址与签名
缓存命中率低（<60%）Analytics 按URL看未命中构成查询参数变体过多（每个参数组合独立缓存）→ 收敛参数集；HTML/动态占比高 → 属正常，核对静态扩展名覆盖
R2 上传失败（rclone）rclone lsd r2: 测连通Token 过期/权限缺失 → R2 控制台重发 Access Key；endpoint 账号 ID 填错 → 对照 §9.3
灰云切换后忘改回DNS 面板 Proxy 列全绿（橙云）源站 IP 暴露风险 → 立即恢复橙云；若 IP 已泄露考虑换 IP（Tunnel 方案无此忧）

14上线检查清单（CDN 部分）

对应《上线检查清单.md》§1/§2 的 CDN 相关项，逐项勾选：

  • [BLOCK] 域名 NS 已托管至 Cloudflare，站点状态 Active
  • [BLOCK] 入口二选一就绪：cloudflared Tunnel（推荐，零开放端口）或 Caddy 源站反代 + CF 橙云 Full (strict)
  • [BLOCK] 防火墙/安全组仅开放 22（SSH）、80/443（仅方案 B）；8000 与 3306 未对公网开放
  • SSL/TLS 模式为 Full (strict)；Always Use HTTPS 开启；Min TLS 1.2
  • Cache Rules 四条基线规则就位（api-bypass / admin-bypass / assets-long / images-cache），验证 cf-cache-status 符合预期（§7.5）
  • WAF Managed Rules + Bot Fight Mode 开启；Rate Limiting 全站防扫规则生效
  • Stripe webhook 地址 https://<域名>/api/payments/webhook 在 Stripe 侧登记且不被 WAF 误拦（§13）
  • 兜底静态页已配置（源站故障时边缘返回品牌页，§10）
  • 外部拨测四链路（首页/加购/搜索/checkout）就绪，1 min 频率，覆盖美/欧
  • 缓存命中率基线记录（上线首日 Analytics 截图留档，目标 >85%）
  • CF_TUNNEL_TOKEN（方案 A）已入 .env，未提交仓库、未进镜像
