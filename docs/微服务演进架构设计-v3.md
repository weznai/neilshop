# 指甲电商独立站 · 微服务演进架构设计（v3.0）
> 本文回答"如果做大需要微服务"的演进规划。核心原则：**今天不建微服务，但今天的每一行代码都不堵死微服务之路**。

---

## 1. 演进总路线（四阶段）

```
阶段0(现在)      阶段1(日千单)      阶段2(日万单)        阶段3(日十万单/多业务线)
─────────────────────────────────────────────────────────────────
单机 Compose  →  3台 K8s          →  部分拆分微服务     →  完整微服务平台
Java单体       仍是Java单体         交易/商品先拆        按域自由扩展
Python AI服务  Python AI服务        +网关+注册中心       多语言并存
Redis Stream   Redis Stream        RocketMQ             RocketMQ/Kafka
```

**反模式警告**：不要一开始就上 Spring Cloud 全家桶。过早微服务 = 用 10 倍运维成本买 0 收益，Netflix/Amazon 都是单体起步、按痛点拆分。

## 2. 领域驱动划分（微服务拆分蓝图）

按 DDD 限界上下文预划 8 个服务，**即使现在是单体，也按这个边界组织 Maven 模块**：

```
┌─────────────────────────────────────────────────┐
│                    Next.js BFF                    │
└───────────────────────┬─────────────────────────┘
                        │
┌─────────┬─────────────┼──────────────┬──────────┐
│trade-svc │product-svc │member-svc     │content-svc│   ← 核心域(先拆)
│ 订单/支付 │ 商品/SKU    │ 会员/积分/RBAC │ 评价/博客 │
│ 库存/退款 │ 分类/集合   │ 地址/登录      │ UGC审核  │
├─────────┼─────────────┼──────────────┼──────────┤
│promo-svc │search-svc  │ai-svc         │notify-svc│  ← 支撑域(后拆)
│ 折扣/捆绑 │ Meili网关   │ 推荐/客服Agent │ 邮件/短信 │
│ 弃购/EDM │ 语义搜索    │ 试戴/生成     │ 模板/频控 │
└─────────┴─────────────┴──────────────┴──────────┘
     │          │            │            │
   MySQL     MySQL        向量库Qdrant    (无库,只转发)
   trade库   product库    +只读副本       RocketMQ
```

**拆分优先级与信号**

| 顺序 | 服务 | 拆分信号（出现才拆） |
|---|---|---|
| 1 | trade-svc | 大促交易洪峰拖垮商品浏览；支付代码发布要全站停机 |
| 2 | search-svc + ai-svc | 搜索/AI 独立扩容需求（GPU 节点分离） |
| 3 | promo-svc + notify-svc | 营销活动频繁，弃购/EDM 量大到影响交易 |
| 4 | product-svc | 商品上新高频，运营后台操作拖慢前台 |
| 5 | member/content | 通常最晚拆，负载一直平稳 |

## 3. 现在就要做的 6 件事（为微服务铺路，成本≈0）

| # | 做法 | 现在收益 | 未来收益 |
|---|---|---|---|
| 1 | **Maven 多模块**：`nailshop-product / nailshop-trade / nailshop-member...` 单体内按域分包，模块间只许走 Service 接口，禁止跨模块查表 | 代码清晰 | 拆分=把模块变进程，接口不变 |
| 2 | **一库一域**：MySQL 建 `nailshop_trade / nailshop_product` 两个 schema，跨域禁止 JOIN，只能调接口 | 数据边界清晰 | 拆分时数据库直接跟着 schema 走 |
| 3 | **事件先行**：领域事件落地（订单已支付/已发货），单体内部用 Spring Event，但事件对象定义为 JSON 契约 | 解耦邮件/积分/索引 | 换 RocketMQ 只换 Binder，消费者不动 |
| 4 | **无状态纪律**：session/购物车全在 Redis，应用零本地状态 | 可水平扩容 | 直接 K8s Deployment |
| 5 | **接口契约化**：内部模块调用写 OpenAPI 注解；Python AI 服务契约先行（FastAPI 自带） | 联调清晰 | 变成 REST/gRPC 服务调用时零改造 |
| 6 | **配置中心思维**：所有配置走环境变量/外部化，代码不含 IP 硬编码 | 多环境方便 | 接 Nacos 无痛 |

## 4. 微服务技术栈选型（阶段 2 启用）

| 组件 | 选型 | 理由（对比备选） |
|---|---|---|
| 框架 | Spring Boot 3 + Spring Cloud Alibaba | 国内生态/中文资料 vs 原生 SC（Netflix 已维护模式） |
| 注册/配置中心 | **Nacos**（2.x 集群×3） | 注册+配置二合一，比 Eureka+Config 少运维一套 |
| 网关 | **Spring Cloud Gateway** | 替代阶段1的 Nginx 应用层路由，限流/灰度在网关做 |
| RPC | OpenFeign(同步) + Dubbo(高性能可选) | 团队熟悉度优先，gRPC 留给 Java↔Python 高频调用 |
| 消息 | **RocketMQ 5.x**（NameServer×2 + 主从 Broker） | 延迟消息(超时关单)/事务消息(订单扣库存最终一致) |
| 熔断限流 | Sentinel（集群流控） | 与 SC Alibaba 无缝 |
| 分布式事务 | Seata AT 模式（尽量少用） | 能用事件最终一致就不用 2PC |
| 链路追踪 | OpenTelemetry + Jaeger | 阶段1就引入 OTel SDK，后期加 Collector 即可视 |
| 部署 | K8s + Helm + Argo CD | GitOps，环境一致性 |
| 观测 | Prometheus + Grafana + Loki + Tempo | 一栈式指标/日志/trace |

**跨语言（Python AI 服务）接入方式**
```
Nacos 注册: nacos-sdk-python 注册到同一注册中心
调用: Java --OpenFeign/HTTP--> ai-svc (网关统一鉴权,服务间内部 JWT)
异步: 双方都收发 RocketMQ topic(rocketmq-client-python)
```

## 5. 拆分后的关键问题预案

### 5.1 数据一致性（最难，提前定规矩）

| 场景 | 方案 |
|---|---|
| 下单扣库存（跨 trade/product） | 优先：Redis 预扣(单库)+ 事件最终一致；兜底：RocketMQ 事务消息 |
| 支付成功发积分（trade/member） | 监听 `order.paid` 事件 + 消费幂等表 + 对账日报 |
| 退款回补库存 | `order.refunded` 事件驱动，T+1 对账修复差异 |
| 原则 | **禁止跨服务分布式事务(Seata)满天飞**，95% 场景事件+幂等+对账够用 |

### 5.2 拆分实操步骤（以 trade-svc 为例，绞杀者模式）
```
① 代码: nailshop-trade 模块 → 独立 Spring Boot 进程(接口不变)
② 数据: nailshop_trade schema → 迁到独立 MySQL 实例,双写过渡1周
③ 流量: Nginx/网关按路径灰度 5%→25%→100% 切到新服务
④ 下线: 单体中移除 trade 代码,旧库只读保留30天
⑤ 演练: 切换前压测新服务达到单体 1.2 倍容量
全程可回滚: 网关切回旧路径即可
```

### 5.3 基础设施演进对照

| 组件 | 阶段0(1台) | 阶段1(3台) | 阶段2(微服务) | 阶段3 |
|---|---|---|---|---|
| 入口 | Caddy | Nginx/Cloudflare | SC Gateway×2 | 网关集群+多地域 |
| 注册配置 | 无(固定地址) | 无 | Nacos×3 | Nacos 多集群 |
| 消息 | Redis Stream | Redis Stream | RocketMQ | RocketMQ 集群+Kafka(日志流) |
| 部署 | Compose | K8s(k3s) | K8s+Helm | 多集群/多区域 |
| 链路 | 日志 traceId | OTel SDK | +Jaeger/Tempo | 全链路+eBPF |
| 机器 | 1×4C8G | 3×4C8G | 6-10 台 | 按服务弹性 |

## 6. 决策检查清单（什么时候真的该拆）

满足 **3 条以上**再动手，否则继续单体优化：

- [ ] 日订单 > 10000，或大促单日 > 50000
- [ ] 研发团队 > 8 人，发布互相阻塞每周发生
- [ ] 单体启动 > 5 分钟，构建 > 20 分钟
- [ ] 某模块负载与其他差异 > 5 倍（如交易 vs 内容）
- [ ] 需要独立伸缩/独立容灾（如交易要求 99.99%）
- [ ] 多业务线复用同一能力（如后续开 TikTok 店中台）

**记住**：拆微服务是为了解决"组织与规模痛点"，不是为了简历好看。按 §3 铺路 + §5.2 绞杀者模式，任何一天想拆都能 2-4 周拆一个服务出去。
