# 指甲电商独立站 · 业务流程闭环与数据模型全景（v1.3）
> 本文是业务层的最终蓝图：**14 条业务闭环流程**（每条含触发→步骤→终态→异常→兜底对账）+ **11 个域完整数据模型**（含新表 DDL 与状态机）。
> 与《业务功能完善度分析.md》的 P0/P1/P2 对应，标注了每条流程的优先级。

## 第二部分 · 14 条业务闭环流程

### 2.1 【P0】订单主流程闭环（父流程）

```
浏览 → 加购 → 结算页 → 创建订单 → 支付 → 履约 → 发货 → 送达 → 完成 → 评价/积分 → 复购唤醒
                                                │
                ┌───────────────┬───────────────┼────────────────┐
                ▼               ▼               ▼                ▼
            超时关单(30min)  支付失败重试     用户主动取消      部分退款
```

**详细时序（含异常分支）**

| 步骤 | 动作 | 数据落点 | 异常与闭环处理 |
|---|---|---|---|
| 1 加购 | Redis cart 写入 + MySQL 镜像 | `carts` | 合并车冲突按 §2.1 详细设计 |
| 2 结算页试算 | 服务端计价（码+积分+运费+税） | 只读 | 试算结果 5min 缓存，下单重算 |
| 3 创建订单 | Redis 预扣库存→落库→Stripe Session | `orders`(status=0)+`order_items`+`payments` | 预扣失败→返回 20002；幂等键防双击 |
| 4 支付回调 | Webhook→幂等表→锁单→状态推进 | `payments`→1, `orders`→PAID | 回调丢失→success 页轮询主动查 Stripe 补单 |
| 5 超时未付 | 定时任务关单 | `orders`→CANCELED(reason=timeout) | 关单前反查 Stripe（防已付未回调） |
| 6 履约 | 后台打单/拣货/发货回填运单号 | `shipments`, `orders`→SHIPPED | 拆单场景见 §2.12 |
| 7 送达 | Shippo Webhook | `orders`→DELIVERED, delivered_at | 7 天无 Webhook→定时任务按 ETA 强制标送达 |
| 8 完成 | 送达+7天 或 用户确认 | `orders`→COMPLETED | 触发积分解冻发放（§2.6） |
| 9 评价邀请 | delivered+3d Klaviyo | — | 见 §2.11 |
| 10 复购唤醒 | 完成后按周期分层 EDM | — | 见 §2.14 |

**终态**：COMPLETED / REFUNDED / CANCELED（三选一，不可逆；REFUNDED 后仍可售后）
**闭环保证**：每个状态跳变写 `order_timeline`；资金对账见 §2.2；库存对账见 §2.3。

### 2.2 【P0】支付与资金对账闭环

```
创建 PaymentIntent → 用户付款 → Webhook(succeeded) → 标记已付 → 后续履约
     │                  │              │
     │                  ├─ 3DS 失败 → Webhook(failed) → 通知用户重付(24h内)
     │                  ├─ 退款 → Webhook(refunded) → payments.refunded_amount 累加
     └─ 未付 → 30min 超时关单（前查 Stripe 防漏）
每日对账: Stripe Balance Transactions(日账单) vs payments 表 vs orders 表
  ├─ 三方金额一致 → 平账
  ├─ Stripe 有、DB 无 → 漏单告警 + 自动补单
  ├─ DB 有、Stripe 无 → 幽灵订单告警（人工介入）
  └─ 部分退款不齐 → 退款同步任务补偿
```

**多支付方式路由（P0 补齐项）**
```
结账页分流: [卡/ApplePay/GooglePay → Stripe] [PayPal] [Klarna BNPL]
统一抽象: payments 表 provider 字段区分; 每家独立 Webhook + 幂等表
退款路由: 原路退回(Stripe/PayPal/Klarna 各自 API), 部分退款金额校验 ≤ 原支付-已退
```

### 2.3 【P0】库存闭环（Redis 预扣 + DB 实扣 + 对账）

```
补货入库 ─→ DB stock 增加 ─→ Redis stock 键预热刷新
   │
下单 ─→ Redis Lua 预扣(hold 登记) ─→ 支付成功: DB 事务实扣 + 清 hold
   │                                    │
   │ 超时/取消 ─→ release 回滚 Redis ──┘  退款退货 ─→ 可选回补(见 RMA)
   │
每日库存对账: ∑(stock_movements 流水) == DB stock 现值 == Redis 现值 - 持有中
   ├─ 不平 → 冻结该 SKU 售卖 + 告警 + 以流水回放修正
   └─ Redis 故障 → 降级 DB 乐观锁扣减(version 字段), 吞吐降但不超卖
```

**库存流水（一切库存变动的唯一真相）**
```
stock_movements: type ∈ {purchase_in(采购入) / hold(预扣) / confirm(实扣) /
  release(释放) / refund_return(退货回补) / adjust_count(盘点调整) /
  adjust_admin(手工调整) / damage(损耗)}
每条必带 ref_type+ref_id(订单/采购单/盘点单) → 任何变动可追溯
```

### 2.4 【P0】退货退款闭环（RMA）——最重要的售后闭环

```
① 用户在 /account/orders 或邮件链接发起退货(选原因+数量)
      │ 前置校验: 订单 DELIVERED/COMPLETED 且 delivered_at ≤ 30天
      │          未超出该单可退数量(已退+已换 + 本次 ≤ 原购)
      ▼
② 生成 RMA 号, status=requested, 通知用户
      ▼
③ 后台审核(自动规则: 客单<$30 且未拆封描述一致 → 自动批; 否则人审)
      ├─ 拒绝 → status=rejected + 原因 + 通知 → 终态(可申诉转工单)
      ▼
④ 批准 → status=approved → Shippo 生成预付退货标签(费用记账)
      ▼
⑤ 用户寄回 → 物流 Webhook 跟踪 → status=in_transit
      ▼
⑥ 仓库收货质检 → status=received
      ├─ 质检不合格(已使用) → status=rejected + 图片证据 → 部分退/不退
      ▼
⑦ 执行退款(原路) → status=refunded
      │ 事务: 原路退款 API → payments.refunded_amount + orders 部分退款标记
      │      库存: 良品回补 stock_movements(refund_return) / 次品 damage
      │      积分: 该商品 earned 按比例回冲; 该单已用积分返还
      │      报表: returns.reason 落库 → 周报"退货原因 TOP"
      ▼
⑧ 闭环反哺: 原因统计(尺码不对/质量问题/不喜欢) →
   尺码不对占比>15% → 触发尺码指南优化任务
```

**退款金额规则表（计价引擎的一部分，避免歧义）**

| 项目 | 是否退 | 说明 |
|---|---|---|
| 商品金额 | ✅ 按实付比例 | 用了折扣码的按分摊后单价退 |
| 运费 | ⚠️ 有条件 | 质量问题全退；无理由不退（政策明示） |
| 税费 | ✅ 按比例 | 随商品退 |
| 积分抵扣部分 | ✅ 返积分 | 不返现金 |
| 该单获得的积分 | ❌ 按退货比例回冲 | 退货商品对应积分作废 |

### 2.5 【P1】换货闭环（美妆 DTC 标配：重发不回收）

```
① 用户发起换货(原商品+原因 → 新甲型/款式, 差价规则: 同价免费/补差/退差)
      │ 校验: delivered ≤ 30天 且 该商品未退过未换过
      ▼
② 后台审核 → approved
      ▼
③ 生成换货出库单(新变体预扣库存) → 直接发货(不等待旧品退回!)
      │ 沙龙级决策: 穿戴甲单价低, 回收运费+质检成本 > 货值 → 重发体验最优
      ▼
④ 新品发货 status=shipped_out → 用户签收 → status=completed
      │ 旧品处置: 用户自行保留(政策写明"无需寄回"作为 goodwill)
      ▼
⑤ 差价结算: 补差→发送支付链接; 退差→原路退
      防滥用: 同一订单同商品最多换 1 次; 风控标记高频换货用户(>2次/季)
```

### 2.6 【P0】积分闭环（获得→冻结→使用→回冲→过期全周期）

```
                ┌──────────────── 积分生命周期 ────────────────┐
下单支付成功         订单完成/评价后        下单使用            退款
────────────→ 获得并冻结 ────────→ 解冻可用 ────────→ 冻结扣除 ────────→ 回冲/作废
 +10分/$1        (交付且过退货期)      (100分=$1抵扣)      (按退货比例)
                │                                           │
签到/评价/推荐奖励 ─→ 直接可用                         180天未使用 → 过期扣减
```

**关键规则（防漏洞）**

| 规则 | 内容 | 防的风险 |
|---|---|---|
| 冻结期 | 支付获得积分冻结，DELIVERED+15 天（退货期后）自动解冻 | 恶意下单刷分再退货 |
| 使用上限 | 单笔抵扣 ≤ 订单金额 50% | 积分党 0 元购套利 |
| 回冲顺序 | 退款时先作废该单 earned（不足再扣余额） | 白嫖积分 |
| 已用返还 | 用积分支付的部分退款 → 返积分非现金 | 现金流漏洞 |
| 过期 FIFO | 按 ledger.expires_at 先到先扣，到期前 7 天邮件提醒 | 沉默成本+用户投诉 |
| 对账 | 每日: ∑ledger.change == users.points 冗余值 | 数据漂移 |

**Ledger reason 全集**：1下单获得(冻结) 2解冻 3评价奖励 4签到 5推荐奖励 6生日礼 7消费冻结扣除 8退款作废 9退款返还 10过期扣减 11管理员调整 12UGC采用奖励

### 2.7 【P1】礼品卡闭环（数字礼品卡）

```
① 购买: 礼品卡作为虚拟商品下单(面额 $25/$50/$100) → 支付成功
      ▼
② 激活: 生成唯一码(GC-XXXX-XXXX) + 初始余额, 发送持卡人邮箱(可转赠)
      │ 注意: 礼品卡订单不产生积分、不参与折扣码
      ▼
③ 消费: 受赠人结算时输入码 → 校验(有效+余额≥抵扣额) → 冻结抵扣
      │ 组合支付: 礼品卡 + 卡/PayPal 补差; 一单可用多张卡
      ▼
④ 支付成功: 扣减余额(ledger 流水) / 支付失败: 解冻
      ▼
⑤ 退款: 原路返还 → 礼品卡支付部分退回礼品卡余额(政策明示)
      ▼
⑥ 余额=0 → status=exhausted; 有效期 5 年(加州法律: 礼品卡不得过期→美区设长期有效+休眠费规则确认)
对账: gift_card_ledger 流水 == 各卡 balance == ∑(售出-消费+退款)
```

### 2.8 【P2·战略】订阅制月盒闭环（LTV 引擎）

```
① 选套餐(4/6/8 周一盒·自选款式/盲盒) → Stripe Billing 创建订阅
      ▼
② 周期扣款(3 天前邮件预告+款式确认窗口) → 自动生成"订阅订单"(标记 source=subscription)
      ├─ 扣款失败 → Dunning: 重试 1/3/5 天(邮件+站内) → 仍失败 → status=past_due → 暂停发货不取消
      ▼
③ 正常履约(走订单主流程 §2.1)
      ▼
④ 生命周期管理:
      暂停(最多3个月/旅行模式) / 换款式 / 换频次 / 跳过一期
      取消: cancel_at_period_end(期末生效,期间可撤销) — 会员制取消摩擦最低方案
      ▼
⑤ 挽回: 取消后 7 天发"85 折回来"邮件; 流失标记 → 沉睡池
      ▼
⑥ 闭环指标: 订阅 MRR / 留存曲线(3月/6月) / 流失原因统计(取消时必选) → 反哺盒型设计
```

### 2.9 【P1】推荐有礼闭环（裂变增长）

```
① 老用户生成专属推荐码/链接(RF-xxxx, 绑定 user)
      ▼
② 新用户经链接注册 → referrals 记录(pending→signed)
      ▼

⑥ 数据闭环: K 因子 = 每用户平均带来首单数; 被推荐用户 LTV vs 自然用户 LTV 对比(渠道质量)
```

### 2.10 【P0】售后工单闭环（客服工作台）

      ▼

      ▼
⑥ 满意度评分(1-5) + 关闭原因统计 → 周报: 工单量/首响时长/解决率/差评工单复盘

      ▼

      ▼
闭环: 差评(≤2星)自动生成工单关联订单 → 客服跟进 → 修改评价率追踪
```

### 2.12 【P1】发货与拆单闭环

```
订单 PAID → 履约队列 → 仓库工作台:
  待打单(生成面单) → 待拣货(扫码校验 SKU) → 待发货(称重交接) → 已发货
      │
      ├─ 一单多包: 甲片仓 + 睫毛仓分开发 → shipments 多行, 每包独立运单号
      │   orders 状态: 全部包发货才 → SHIPPED; 部分发货 status=PARTIAL_SHIPPED(新增状态)
      │
      └─ 面单作废/换承运: 作废面单 → 重新打单(记 timeline)
物流跟踪: Shippo Webhook → 更新 shipments.status
   异常件(滞留>5天/派送失败/地址错误) → 自动生成 P0 工单 + 客服介入
送达: 全部包 delivered → orders→DELIVERED
```

### 2.13 【P1】到货通知闭环（缺货流量回收）

```
缺货变体详情页 → "到货通知我"按钮 → stock_notifications 落库(同变体同邮箱唯一)

### 2.14 【P1】用户生命周期营销闭环（总纲）

```
        ┌─ 新客线: 首访弹窗(WELCOME20) → 未注册 3d 提醒 → 首购 → 欢迎邮件(品牌+尺码指南)
        │
生命周期 ─┼─ 复购线: 完成后 21d(美甲更换周期!) → "该换款式了"邮件(关联上次购买系列)
        │         售后满意(工单好评/5星评价) → 30d 交叉销售(买甲片的推睫毛)
        │
        ├─ 弃购线: §详细设计 4.6(1h/24h/48h 阶梯码) → 恢复购物车深链
        │
        └─ 沉睡线: 60d 未购 → 唤醒 9 折 / 90d → 会员专享 / 180d → 清池(降频至月度)
每条线都有: 触发条件 + 频控上限 + 转化指标 + 退出条件 = 闭环
全局频控: 单用户营销邮件 ≤ 4 封/周(合规+体验), 退订中心可按线开关
```

## 第三部分 · 完整数据模型（11 域全量 DDL）

> 延续详细设计的全局约定（utf8mb4 / DECIMAL(10,2) / TINYINT 枚举 / DATETIME(3) UTC / 软删状态位）。以下仅列**新增与变更**表，基础表见 v1.1 详细设计 §2。

## 第四部分 · 状态机与状态流转总表（防"状态黑洞"）

> 状态黑洞 = 订单/单据停在某个状态永远出不来。以下每台状态机都定义了**超时出口**。

| 单据 | 状态机 | 超时出口（兜底） |
|---|---|---|
| orders | 待付→已付→(部分发)→已发→送达→完成；取消/退款 | 待付 30min→自动取消(前查Stripe) |
| payments | 待付→成功/失败；退款累加 | 24h 无回调→主动查 API |
| shipments | 待打单→已打→待交接→运输→送达/异常 | 运输 15 天未达→异常→工单 |
| returns(RMA) | 申请→批准→标签→在途→收货→退款/拒绝 | 批准后 21 天未寄回→自动关闭 |
| exchanges | 申请→批准→(差价)→发货→完成 | 待差价 48h 未付→自动取消 |
| tickets | 新→处理中→等用户→待关→关闭 | 等用户 48h→自动关；处理中 72h→升级提醒 |
| reviews | 待审→通过/拒绝 | 待审 72h→提醒运营(不自动通过,防风险) |
| gift_cards | 待激活→有效→用尽/冻结/作废 | 待激活 24h 未支付→作废 |
| subscriptions | 生效→(暂停/past_due/期末取消)→取消 | past_due 5 天重试→暂停+挽回流 |
| referrals | 注册→首单待确认→已奖励/无效 | 首单待确认 45 天(过退货期)→发奖 |
| purchase_orders | 草稿→已下单→部分到货→全部到货/取消 | 超期 7 天未到→提醒跟单 |

**统一规则**：所有状态机跳变 = DB 事务内完成（更新单据 + 写 timeline/流水），失败整体回滚，不存在"改了状态没写流水"。

## 第五部分 · 三大对账闭环（钱/货/分）

### 5.1 资金对账（每日凌晨）

```
Stripe Balance Transactions(昨日)
  = payments 表(昨日成功+退款) ?
  = orders 表金额合计 ?
→ 差异写入 reconciliation_daily(diff≠0 → P0 告警 → 人工处理后标记)
含: PayPal/Klarna 各自对账单 API 同样流程
```

### 5.2 库存对账（每日 + 事件触发）

```
DB stock 现值 = 初始 + ∑stock_movements ?   (不等→以流水回放修正+告警)
Redis 可售 = DB stock - 持有中 hold 集合 ?  (不等→重预热)
滞销预警: 60 天无出库 SKU → 周报
```

### 5.3 积分对账（每日）

```
users.points 冗余 = ∑points_ledger.change ?
礼品卡: balance = 初始 - ∑消费 + ∑退款 ?
差异>0 → 冻结相关账户积分功能 + 告警
```

## 第六部分 · 优先级与排期映射

| 闭环流程 | 优先级 | 对应表 | 建议排期 |
|---|---|---|---|
| 订单/支付/库存/评价/工单/RMA/合规 | P0 | §3.3/3.4/3.6/3.8/3.9 | MVP W1-W8 |
| 换货/拆单发货/到货通知/礼品卡/推荐/生命周期营销/库存流水化/采购 | P1 | §3.4/3.5/3.7 | 上线后 1-2 月 |
| 订阅月盒/储值/多语言 | P2 | §3.5 | 3-6 月战略期 |

**总原则**：每上一条新流程，同步上它的**对账与超时出口**——没有兜底的流程不允许上线。
