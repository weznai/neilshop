## 2. 分层高可用设计

### 2.1 接入层（用户永远"打得开"）

| 措施 | 说明 |
|---|---|
| Cloudflare | DNS 多活 + WAF + 静态资源 CDN，源站故障时静态页仍可服务 |
| 健康检查 | SLB 主动探测 `/actuator/health`（Spring）与 `/api/health`（Next），异常节点 30s 摘除 |
| 故障转移 | Nginx upstream 配 `max_fails=3 fail_timeout=30s` 自动踢节点 |
| 降级页面 | 全挂时 Cloudflare Serve Rules 返回兜底静态页（含客服邮箱/品牌墙），保住品牌 |

### 2.2 应用层（无状态 + 多副本）

- **会话外置**：JWT + Redis session，任一实例可处理任一请求，滚动发布零丢会话
- **优雅停机**：SIGTERM → Spring `server.shutdown=graceful` + K8s `preStop` 探活摘流量，等 30s 排空
- **过载保护**：
  - Sentinel/Resilience4j 熔断：AI 服务超时 300ms、错误率 >50% 自动熔断 30s
  - 舱壁隔离：下单/支付线程池与商品浏览隔离，浏览洪峰不打垮交易
  - Nginx 限流：`limit_req` IP 60r/min，checkout 接口独立更高阈值
- **降级策略矩阵**（核心！交易优先，其余可降）：

| 依赖故障 | 降级动作 | 用户感知 |
|---|---|---|
| AI 推荐挂 | 返回运营配置的热销榜 | 几乎无感 |
| 语义搜索挂 | 回退 Meilisearch 关键词 | 搜索变"笨"一点 |
| 客服 Agent 挂 | 显示人工客服入口 | 略慢 |
| 评论分析挂 | 评价改人工审核队列 | 无感 |
| Meilisearch 挂 | 回退 MySQL LIKE + 缓存 | 搜索慢但仍可用 |
| Klaviyo 挂 | 事件落库 `marketing_events` 表，恢复后重放 | 邮件晚到 |

### 2.3 数据层（RPO/RMA 目标）

**MySQL（资金与订单，最高等级）**
```
1主2从 · 半同步复制(replication semi-sync)
故障转移: Orchestrator/ORC 自动选主(30s内) + ProxySQL/HAProxy 感知切流
备份: 每日全备(XtraBackup) + binlog 实时归档到 R2 · RPO<5min
演练: 每季度手动主从切换演练; 从库延迟>30s 告警
读写分离: 写走主,读走从(订单详情/后台报表);
         资金相关(库存扣减/支付状态)强制读主,防读到旧数据超卖
```

**Redis（购物车/库存/会话，第二等级）**
```
哨兵模式 3节点(1主2从+3哨兵跨可用区)
客户端: Spring Data Redis + Lettuce 读从写主,哨兵拓扑自动刷新
持久化: AOF everysec + RDB 每小时,故障重启优先 AOF
兜底: 购物车在 MySQL carts 表有镜像(§4.3),Redis 全丢可从镜像恢复
库存键: Redis 故障期间切"DB 乐观锁降级扣减"(version 字段),吞吐降但绝不超卖
```

**Meilisearch / Qdrant（可重建，第三等级）**
```
索引 = MySQL 的可重建投影: 每日快照 + 变更 CDC(监听 binlog/业务双写) 同步
单点故障: 30s 内切备节点,数据最多回退到最近同步点(搜索场景可接受)
```

### 2.4 异步与最终一致

- **本地消息表**：订单创建/支付成功等事件先落 `outbox` 表（与业务同事务），MQ/Job 拉取投递，保证"落库必达"
- **MQ 镜像队列**：弃购、邮件、索引同步走 MQ，单节点故障消费自动转移
- **Webhook 重放**：Stripe 事件已幂等（webhook_events 表），失败进重试队列，指数退避 1m/5m/30m/2h

## 3. 大促/流量高峰预案（穿戴甲上新高发场景）

| 阶段 | 触发 | 动作 |
|---|---|---|
| 预热(上线前) | 运营配置 | 预乘扩容 Java×4、Next×4；Redis 预热热销商品缓存；CDN 预热 Hero 图 |

| 兜底 | 全站不可用 | Cloudflare 静态兜底页 + 已下单用户短信/邮件通告 |

## 5. 发布与容灾

### 5.1 发布策略
- 全服务容器化（Docker），K8s/Docker Swarm 或双云主机+SLB 起步
- **滚动发布**：maxSurge=1 maxUnavailable=0，健康检查通过才切流量
- **灰度发布**（P2 后）：Cookie/地域 5%→25%→100% 灰度新版本
- 数据库迁移只做向后兼容变更（加列不加删列），新老代码共存期可回滚

### 5.2 备份与恢复（RTO/RPO 承诺）

| 资产 | RPO | RTO | 方式 |
|---|---|---|---|
| MySQL | <5min | <30min | XtraBackup 每日 + binlog PITR + 每季度恢复演练 |
| Redis | <1min(AOF) | <5min | AOF+RDB；购物车另有 MySQL 镜像兜底 |
| 商品图片 | 0 | — | R2 版本化 + 跨区复制 |
| 配置/密钥 | 0 | — | Git+Vault，异地备份 |
| 索引(Meili/Qdrant) | 可重建 | <1h | 全量重建管道 |

### 5.3 每月容灾演练清单
- [ ] 手动 kill 一个 Java 实例 → 流量自动切走，无 5xx 尖刺
- [ ] Redis 主节点宕机 → 哨兵 30s 切换，购物车可用
- [ ] MySQL 主从切换演练（低峰期）→ 应用自动重连
- [ ] Stripe Webhook 断网 10min → 恢复后事件重放补单，对账平
- [ ] AI 服务熔断 → 前台热销榜兜底展示

## 6. Java + Python 服务化细节（v2.0 新增）

### 6.1 职责与边界
```
Spring Boot 主服务 = 唯一可信数据源入口(写) + 交易全链路
FastAPI AI 服务    = 只读 + 计算,不直连业务库(读从库副本/Redis/向量库)
```

### 6.2 服务间调用规范
```
同步(推荐/搜索): Java --Resilience4j(超时300ms/熔断/降级)--> FastAPI /recommend
  · 降级: 返回缓存的热销榜单(Redis: rec:fallback, 每10min刷新)
  · 鉴权: 服务间内部 JWT(HS256, 60s 有效), 不暴露公网, 内网/K8s NetworkPolicy 隔离
异步(评论分析/预测): RocketMQ topic: review.created / sales.daily
  · Python 消费失败自动重试, 死信队列人工处理
```

### 6.3 AI 能力落地节奏（避免过度建设）
| 阶段 | 能力 | 依赖 |
|---|---|---|
| P2 | 个性化推荐(协同过滤+热销兜底) | 行为事件 → Redis 特征 |
| P2 | 智能客服 Agent(LLM+RAG, 政策FAQ) | 政策文档向量化(Qdrant) |
| P3 | 语义搜索(向量召回混合排序) | 商品向量 + Qdrant |
| P3 | AI 试戴/款式生成 | SD/Flux API(Replicate), GPU 外置免运维 |

## 7. 部署拓扑参考（MVP 落地，控制成本）

### 7.0 方案零：单机起步（0-日百单阶段，最省）

前期量不到时**一台完全可以**，核心原则：**单机也要"为扩展而建"**——所有组件容器化、配置外置、域名走 Cloudflare，后面加机器就是"加入"而不是"重搭"。

```
单机(4C8G 或 8C16G)
├─ Docker Compose 一把梭:
│   ├─ next(app)          # 前端 SSR
│   ├─ java(app)          # Spring Boot 主业务
│   ├─ fastapi(app)       # AI 服务(量小可后置,先不部署)
│   ├─ mysql:8            # 数据(每日自动备份到 R2/OSS)
│   ├─ redis:7            # AOF 开启
│   ├─ meilisearch        # 可选,前期 MySQL LIKE 也够
│   └─ caddy/nginx        # 反代+自动 HTTPS
└─ Cloudflare(DNS/CDN/WAF) # 前置,静态资源+缓存挡掉大半流量
```

**单机阶段的"穷人高可用"（很重要）**

| 风险 | 对策 |
|---|---|
| 整机宕机 | ①Cloudflare 兜底静态页（品牌页+客服邮箱）；②云快照每日自动备份，同规格重建 30-60min 恢复 |
| 数据丢失 | MySQL 每日 XtraBackup/mysqldump + binlog 上传 R2/OSS（**这是单机阶段唯一不可妥协的**），RPO 可压到 5-10min |
| 流量突刺 | Cloudflare 缓存+Rate Limiting 挡；静态资源全走 CDN，源站只承受动态请求 |
| 磁盘坏/误删 | 备份必须**异地**（对象存储），不能只存在本机 |
| 发布翻车 | Compose 镜像版本固定，一键回滚 `docker compose` 到上一版本 |

**单机成本**：4C8G ≈ $40-80/月（国内 ¥150-400），加上 CDN/备份/托管 Redis（可选）≈ **$100/月内**。

**单机的容量天花板**（经验值，容器混部 8C16G）：日 PV 10-30 万 / 日订单 3000-8000 单无压力；穿戴甲 DTC 早期远达不到，可安心跑到日千单再扩。

**单机 → 3 台的平滑演进（设计已预埋）**
```
第1步 加机器2: docker compose 迁移为 K8s(k3s 轻量版)/或继续 compose:
             MySQL 改 1主1从, Java/Next 双机+Cloudflare 摘流量
第2步 加机器3: 变成 §7.2 方案乙拓扑(Redis 建议此时换托管主备)
第3步 流量再涨: 回到 §7.1 方案甲(4台双AZ)
全程: 代码零改动 —— 因为从第一天起就是 无状态应用+外置DB连接串+Cloudflare域名
```

**单机阶段唯一的纪律**：备份脚本 + 每月一次恢复演练（从 R2 拉备份在本地起一个 MySQL 验证可恢复）。没有验证过的备份等于没有备份。

### 7.1 方案甲：双 AZ · 4 台（标准 HA，$400-600/月）

```
区域: 单区域双可用区(如 AWS us-east-1a/1b 或 阿里云双AZ)

可用区A:  Nginx主 / Java×1 / Next×1 / MySQL主 / Redis主 / Meili主
可用区B:  Nginx备 / Java×1 / Next×1 / MySQL从 / Redis从+哨兵 / Meili备
托管层:   R2/S3(图) · Cloudflare(DNS/WAF/CDN) · Stripe/Klaviyo(第三方)
CI/CD:   GitHub Actions → 构建镜像 → 镜像仓库 → 滚动部署
```
MVP 月成本估算（AWS/阿里云同级）：双 AZ 4 台 4C8G ≈ $400-600/月 + 托管服务 $100 内，即可达成 99.9% 可用性目标。

### 7.2 方案乙：3 台机器部署方案（紧凑 HA，推荐起步）

3 台机器做高可用的核心思路：**用 Cloudflare 承担入口层，省掉 Nginx 主备两台**；数据层最小冗余=1主1从，第三台跑应用+仲裁。

```
        Cloudflare(DNS/WAF/CDN/健康检查+故障转移)   ← 入口高可用交给云,免机器
                          │
        ┌─────────────────┼──────────────────┐
        │        [K8s 集群 3 节点]            │   每台都跑应用,Pod 反亲和打散
        └─────────────────┴──────────────────┘

节点1(4C8G): Java×1 · Next×1 · MySQL主 ─┐
节点2(4C8G): Java×1 · Next×1 · MySQL从 ─┤ MySQL 1主1从半同步
节点3(4C8G): FastAPI·Meili·Redis(1主+哨兵)┘
             + 第三台同时部署: 哨兵仲裁 / K8s control-plane(轻量)
```

**节点分工明细**

| 节点 | 应用负载 | 数据角色 | 说明 |
|---|---|---|---|
| 节点1 | Java + Next | MySQL 主 | 交易主节点 |
| 节点2 | Java + Next | MySQL 从 | 主挂提升为新主(手动/orchestrator 单容器) |
| 节点3 | FastAPI(AI) + Meili + Qdrant | Redis 主 + 3 哨兵(含仲裁) | 轻数据节点 |

**3 台下的关键取舍与对策**

| 问题 | 对策 |
|---|---|
| Redis 只有 1 主无从 | ①开 AOF everysec + RDB；②购物车有 MySQL 镜像兜底(§2.3)；③Redis 挂=全站不可用 → 用云托管 Redis(¥100/月)替换自建是更优解 |
| MySQL 从库单点 | Orchestrator 单容器自动切主；接受"从库挂=只读降级"，写不受影响 |
| 应用与数据混部 | K8s resource limits 隔离(CPU/内存 request/limit)；MySQL 独占 cgroup，防 Java OOM 拖垮库 |
| 单节点整机宕机 | Cloudflare 健康检查 30s 摘除；MySQL 自动切主；其余 2 台承载全量(容量按 60% 水位规划) |
| 大促扩容 | 3 台是"底座"，洪峰时临时加 1-2 台云主机 Join K8s, 会后释放 |

**Redis 更省心的替代**（3 台方案强烈建议）
```
自建 Redis 单点(风险) → 换云托管 Redis 主备版(阿里云/腾讯云 ≈ ¥80-150/月)
好处: 挂了云厂商自动切,省去哨兵运维,3 台机器全部留给应用+MySQL
```

**成本**：3 台 4C8G ≈ $300-450/月（或国内 ¥1500-2500/月）+ 托管 Redis + CDN 流量 ≈ **$400/月内**，可用性仍可达 99.9%（入口由 Cloudflare 兜底，数据层最小冗余齐全）。

**演进路径**：3 台 → 流量涨 → 加节点4(纯应用) → 加节点5(MySQL 第二从+Redis 副本) → 回到方案甲拓扑。K8s + 反亲和的部署方式保证加节点只是"加入集群"，无需重搭。

### 7.3 方案对比

| | 方案零(1台) | 方案乙(3台) | 方案甲(4台双AZ) |
|---|---|---|---|
| 月成本 | $100内 | $300-450 | $400-600 |
| 可用性 | 99.5%(宕机30-60min恢复) | 99.9%(入口靠 Cloudflare) | 99.9%+ |
| 数据安全 | 异地备份 RPO<10min | 主从半同步 | 主从半同步+多从 |
| Redis | 单机 AOF | 建议托管主备 | 自建哨兵 1主2从 |
| 抗整节点故障 | 靠快照重建 | 任意 1 台,自动化 | 任意 1 台,自动化 |
| 适用 | 0-日千单 MVP | MVP~日千单 | 大促常态化 |
| 扩容 | →直接加机到3台拓扑 | 加节点即入集群 | 加应用机 |
